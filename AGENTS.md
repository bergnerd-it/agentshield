# AGENTS.md

This file defines mandatory repository instructions for AI coding agents, including Junie. It applies to the entire repository unless a more specific `AGENTS.md` exists in a subdirectory.

## 1. Project Mission

AgentShield is a local security proxy for coding-agent traffic. Version 1 inspects traffic explicitly routed through its OpenAI- and Anthropic-compatible endpoints and applies deterministic data-protection policies.

The primary design objective is **preventing accidental disclosure without making claims the implementation cannot enforce**. Security, privacy, protocol correctness, and testability take precedence over feature count.

## 2. Mandatory Reading Order

Before changing code, read these files in the planning/ folder completely:

1. `AgentShield_V1_Specification.md`
2. `docs/ARCHITECTURE.md`
3. `docs/THREAT_MODEL.md`
4. `SECURITY.md`
5. all accepted ADRs in `docs/adr/` relevant to the change
6. `docs/TESTING.md` when changing production code or tests

For milestone work, read the entire milestone and its Definition of Done before editing.

## 3. Scope Discipline

- Implement only the milestone or task explicitly requested.
- Do not begin a later milestone because it appears convenient.
- Do not introduce TLS interception, operating-system firewall changes, a full internet forward proxy, MCP proxying, Tauri, Rust, cloud services, RBAC, or SSO in Version 1 unless the specification is formally changed.
- Do not convert the modular monolith into microservices.
- If a requested change conflicts with the specification or an accepted ADR, stop and identify the conflict before coding.
- Record an approved architectural deviation in a new ADR. Do not silently rewrite an existing accepted ADR to hide a changed decision.

## 4. Security Invariants

These rules are non-negotiable:

- Never disable TLS certificate verification.
- Never forward local AgentShield credentials to an upstream provider.
- Never send provider credentials to the frontend.
- Never store provider credentials in SQLite, source files, fixtures, logs, exceptions, telemetry, snapshots, or audit exports.
- Never log raw request or response payloads by default.
- Never persist detected secret values.
- Never rehydrate secrets, passwords, tokens, private keys, or credentials.
- Never make external provider calls from automated tests.
- Never use real-looking live credentials in tests or documentation. Use clearly synthetic values.
- Never use wildcard CORS.
- Never treat the frontend as an authorization boundary.
- Never forward a request after its client disconnects or its approval expires.
- Never silently bypass a required detector after an error.
- Never add an unencrypted fallback when the native credential store is unavailable.
- Bind locally to `127.0.0.1` by default, not to all interfaces.

When a safe outcome is ambiguous, fail closed for credentials and strict-mode required checks. Preserve a clear, actionable error for the user without including confidential content.

## 5. Architecture Rules

- Keep domain models, detectors, redaction, policy evaluation, and audit decisions independent of FastAPI.
- Use adapters for OpenAI, Anthropic, credential stores, persistence, clocks, coding-agent integrations, and future external services.
- A detector returns findings; only the policy engine chooses a `PolicyAction`.
- Maintain action precedence:

```text
BLOCK > REQUIRE_APPROVAL > REDACT > WARN > ALLOW
```

- Preserve unknown provider payload fields unless a security rule explicitly rejects them.
- Keep request scanning complete before sending any outbound request bytes upstream.
- Use bounded buffers and queues. Never buffer a complete SSE response without an explicit, documented size bound.
- Use dependency injection for provider clients, time, IDs, persistence, and credential-store access in tests.
- Keep management API authentication separate from proxy API authentication.
- Keep SQLite as the Version 1 runtime source of truth for policies. YAML is an import/export format.

## 6. Privacy-Safe Engineering

- Prefer metadata, counts, categories, and keyed fingerprints over content retention.
- Use a centralized safe-logging layer. Do not pass arbitrary provider exceptions directly to logging.
- Treat `repr()` and validation errors as possible disclosure paths.
- Redact secrets before they can enter logs or audit records, including error paths.
- Keep reversible pseudonym mappings in memory or protected storage with a TTL.
- Replace only exact placeholders generated by AgentShield.
- Add a regression test whenever fixing a potential data-disclosure bug.
- Test logs, audit rows, API responses, and rendered DOM for absence of every synthetic secret used in a test.

## 7. Backend Standards

- Use Python 3.14 and `uv`.
- Put application packages below `backend/src/agentshield/`.
- Use complete type annotations for application code.
- Keep Pyright in strict mode.
- Use Ruff for formatting and linting.
- Use Pydantic at API and configuration boundaries, not as a replacement for all domain types.
- Use SQLAlchemy 2 style APIs and Alembic migrations.
- Use async I/O on proxy request paths. Do not place blocking NLP or file operations on the event loop.
- Convert failures to the documented safe Problem Details format.
- Do not catch `Exception` merely to continue. A broad catch must have a documented boundary, safe reporting, and defined failure behavior.
- Do not add dependencies when the standard library or an existing dependency provides a clear and secure solution.

Expected backend quality commands after bootstrap:

```bash
cd backend
uv sync --frozen
uv run ruff format --check .
uv run ruff check .
uv run pyright
uv run pytest
```

## 8. Frontend Standards

- Use React 19, TypeScript strict mode, Vite, and pnpm.
- Use the generated OpenAPI client. Do not duplicate backend DTOs manually.
- Keep provider keys and raw secrets out of frontend state, browser storage, URLs, error messages, analytics, and the DOM.
- All state-changing operations require authenticated backend calls.
- Provide accessible labels, focus states, keyboard operation, and clear loading/error/empty states.
- Monaco-based content views must default to sanitized content.
- Avoid a global state library until application state demonstrably requires one; use TanStack Query for server state.
- Do not add server-side rendering or Next.js to the local dashboard.

Expected frontend quality commands after bootstrap:

```bash
cd frontend
pnpm install --frozen-lockfile
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm exec playwright test
```

## 9. Testing Rules

- Follow `docs/TESTING.md`.
- Start with a failing test for a bug or new security behavior whenever practical.
- Use local mock provider servers for contract and streaming tests.
- Test success, denial, cancellation, timeout, malformed input, and upstream failure paths.
- Keep tests deterministic: inject clocks, IDs, random sources where required, and avoid real network calls.
- Mark no security test as skipped merely to make CI pass without documenting and resolving the cause.
- Do not update snapshots blindly. Review them for accidental confidential content and semantic changes.
- Every detector requires positive, negative, boundary, encoding, and false-positive tests.

## 10. Documentation Rules

- Update documentation in the same change as behavior.
- Update `docs/THREAT_MODEL.md` when a new trust boundary, data path, or security control is introduced.
- Add or supersede an ADR for significant architecture changes.
- Keep the README honest about implemented versus planned features.
- Do not claim that Version 1 controls traffic that does not traverse AgentShield.
- Do not claim GDPR compliance, complete PII detection, or complete exfiltration prevention.
- Examples must contain synthetic credentials and fictional personal data.

## 11. Change Procedure

Before editing:

1. inspect repository status and existing user changes;
2. identify the active milestone and acceptance criteria;
3. list affected trust boundaries and security invariants;
4. produce a short implementation plan;
5. inspect existing tests and interfaces.

During implementation:

1. make the smallest coherent change;
2. preserve unrelated user changes;
3. add or update tests with the implementation;
4. keep migrations backward-safe where possible;
5. document assumptions and security consequences.

Before completion:

1. run relevant focused tests;
2. run full linting, type checking, unit, integration, and applicable end-to-end tests;
3. inspect output for leaked synthetic secrets;
4. verify the milestone acceptance criteria;
5. summarize changed files, tests, limitations, and follow-up work;
6. do not start the next milestone.

## 12. Dependency and Supply-Chain Policy

- Use stable releases and commit lockfiles.
- Prefer mature, maintained libraries with compatible licenses.
- Document the purpose of security-sensitive dependencies.
- Do not execute unpinned remote scripts in CI.
- Generate an SBOM for release artifacts.
- Run dependency vulnerability scanning in CI.
- Do not auto-merge dependency changes that affect networking, parsing, authentication, cryptography, credential storage, or security detectors.

## 13. When to Stop and Ask

Stop and request a decision when:

- provider compatibility requires weakening a security invariant;
- a credential would need unencrypted storage;
- the requested behavior changes a trust boundary;
- direct egress enforcement is expected from the cooperative proxy;
- a detector failure has no specified fail-open/fail-closed behavior;
- a new dependency materially changes licensing or distribution;
- existing user changes conflict with the requested implementation;
- a platform cannot provide the required secure credential-store behavior.

Do not resolve these situations through an undocumented convenience workaround.
