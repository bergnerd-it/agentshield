# AgentShield – Version 1 Specification

Status: implementation specification  
Primary target platform: macOS  
Additional target platforms: Linux and Windows  
Working name: **AgentShield** (may be changed later)

## 1. Assignment for Junie

Implement a locally running application that acts as a controlled reverse proxy between a coding agent and external LLM providers. It must inspect outbound requests and inbound responses, detect sensitive content according to configurable rules, and apply a policy decision to allow, record, pseudonymize, require approval for, or block the exchange.

The application consists of:

- an asynchronous Python backend;
- an OpenAI- and Anthropic-compatible LLM proxy;
- a browser-based frontend served by the backend;
- a local database for configuration and privacy-preserving audit events;
- an extensible detector and policy engine.

Implementation must proceed incrementally in the order defined in Section 19. After each milestone, all existing tests must continue to pass.

## 2. Product Goal

AgentShield makes it visible and controllable which data a coding agent sends to an external LLM. In particular, it should prevent credentials, personal data, or project-specific confidential terms from being sent accidentally to an unapproved provider.

Version 1 is a **cooperative LLM reverse proxy**. It controls only requests that are routed through AgentShield. It does not claim to enforce all network traffic generated by a process or computer.

## 3. Version 1 Scope

### 3.1 Included in Version 1

- OpenAI Responses API;
- OpenAI Chat Completions API where this can be added with reasonable effort;
- Anthropic Messages API;
- non-streaming and SSE-streaming requests;
- structured tool calls and tool results contained in provider payloads;
- request and response inspection;
- detection of secrets, PII, and project-specific terms;
- the actions `ALLOW`, `WARN`, `REDACT`, `REQUIRE_APPROVAL`, and `BLOCK`;
- local manual approval through the browser UI;
- consistent and, for eligible data classes, reversible pseudonymization;
- three predefined security profiles;
- privacy-preserving audit records;
- configuration assistance for Codex and Claude Code;
- diagnostic and rollback functions;
- macOS support and platform-neutral implementation for Linux and Windows.

### 3.2 Excluded from Version 1

- transparent TLS interception or installing a custom root CA;
- guaranteed prevention of direct network access outside the proxy;
- operating-system firewall modification;
- a complete forward proxy for arbitrary internet traffic;
- a complete MCP proxy;
- sandboxing or container isolation of the coding agent;
- a Tauri desktop application, menu-bar application, or automatic updater;
- a Rust networking core;
- multi-user operation, RBAC, SSO, or central team management;
- cloud hosting;
- PostgreSQL as a required runtime dependency;
- automatic LLM-based semantic classification of an entire source tree;
- support for images, audio, and arbitrary binary files.

Unsupported binary or multimodal content must be blocked in the strict profile and clearly reported in the other profiles.

## 4. Security Model

### 4.1 Protected Data

- API keys and personal access tokens;
- passwords and bearer tokens;
- private keys and credentials;
- personally identifiable information;
- internal project, customer, and product names;
- configurable package, class, table, and field names;
- other content defined by project-specific rules.

### 4.2 Trust Boundaries

- The backend, local database, and operating-system credential store are trusted components within the Version 1 model.
- Coding agents, LLM providers, web content, and future MCP servers are not automatically trusted.
- The React frontend is not a security boundary. The backend must enforce every decision.
- Connections from AgentShield to a provider must use normal TLS certificate validation. Disabling certificate validation must not be offered as a configuration option.

### 4.3 Known Limitations

- An agent can bypass AgentShield if it has direct network access and does not use the configured proxy.
- Automated detectors can produce false positives and false negatives.
- AgentShield alone does not establish GDPR compliance or guarantee complete prevention of data exfiltration.
- These limitations must be documented in `docs/THREAT_MODEL.md` and displayed clearly in the UI.

## 7. Runtime and Operation

### 7.1 Development Mode

- The backend and Vite development server may run separately.
- CORS may be enabled only for the explicitly configured local development origin.
- Provider keys loaded from `.env` are permitted only in development mode and must cause a visible warning.

### 7.2 Production Mode

- The backend serves the built React frontend from the same origin.
- The service binds to `127.0.0.1` by default.
- The default port is `8765`. On collision, stop with a clear error or select and display an available port.
- Required CLI entry points:

```bash
agentshield start
agentshield doctor
agentshield configure codex
agentshield configure claude-code
agentshield rollback codex
agentshield rollback claude-code
```

- `start` launches the backend and UI and may optionally open the default browser.
- Repeated `start` calls must not create competing instances.

## 8. Local Authentication and Credentials

- Generate a cryptographically random local administration token on first start.
- The management API and proxy API use separate local tokens.
- Tokens must never appear in URLs.
- The browser uses a secure local session or suitable bearer mechanism protected against foreign origins.
- Validate `Host` and `Origin` strictly.
- Wildcard CORS is prohibited.
- Store real provider API keys in the native operating-system credential store.
- The coding-agent profile receives only a local proxy token. Never forward it upstream.
- The backend substitutes the appropriate provider credentials for local credentials.
- Provider credentials must never reach the frontend, exceptions, logs, audit records, or OpenTelemetry attributes.
- If no usable credential store exists, fail safely with an actionable message. Do not silently fall back to unencrypted storage.

## 9. Proxy Endpoints

Implement at least:

```text
POST /proxy/openai/v1/responses
POST /proxy/openai/v1/chat/completions
POST /proxy/anthropic/v1/messages
```

### 9.1 Forwarding Requirements

- Process the request body and relevant headers before making an upstream request.
- Do not forward hop-by-hop headers.
- Never forward local authentication headers.
- Preserve required provider-specific headers and unknown payload fields wherever it is safe to do so.
- Preserve the semantic meaning of upstream status codes and relevant response headers.
- Do not collapse provider error responses into generic HTTP 500 responses.
- Client cancellation must cancel the upstream request.
- Automatic retries are disabled by default for LLM requests that are not clearly idempotent.
- Timeouts and maximum request and response sizes are configurable.
- Process compressed content only if it can be decompressed safely under a strict decompression limit.
- Detect and block proxy loops.

### 9.2 Streaming

- Forward SSE without buffering the complete response.
- Response scanners may use a bounded rolling buffer.
- Respect backpressure.
- Measure time to first byte and added proxy overhead.
- If a blocking finding is detected during a stream, terminate the stream and record the event.
- Do not interpret incomplete or fragmented JSON/SSE data as complete events.

## 10. Common Domain Model

Implement framework-independent domain models equivalent to:

```python
class Finding:
    id: UUID
    category: FindingCategory
    severity: Severity
    detector: str
    confidence: float
    location: FindingLocation
    start: int | None
    end: int | None
    fingerprint: str
    suggested_replacement: str | None
    metadata: dict[str, str]

class PolicyDecision:
    action: PolicyAction
    findings: list[Finding]
    matched_rule_ids: list[str]
    reason: str
    policy_version: str
```

`PolicyAction` contains:

```text
ALLOW
WARN
REDACT
REQUIRE_APPROVAL
BLOCK
```

When several findings apply, use this precedence:

```text
BLOCK > REQUIRE_APPROVAL > REDACT > WARN > ALLOW
```

A detector reports findings only. It must not make the final authorization decision. This separation is mandatory.

## 11. Detector Engine

### 11.1 Interface

Every detector implements a shared asynchronous interface. A detector receives a normalized scan context and returns findings. Detectors must be independently enabled, configured, and tested.

### 11.2 Secret Detectors

Version 1 detects at least:

- OpenAI- and Anthropic-style API keys;
- AWS access key IDs and typical secret assignments;
- GitHub personal access tokens;
- bearer tokens;
- JWTs;
- PEM-encoded private keys;
- passwords in common configuration assignments;
- generic high-entropy values only when accompanied by suitable context.

Tests must use clearly synthetic values only.

### 11.3 PII Detectors

At minimum:

- email addresses;
- telephone numbers;
- IBANs;
- IP addresses, configurable;
- person and organization names through Presidio where supported by the configured language model;
- German and English text.

The UI must display confidence and detector name. Documentation must state that PII detection can be incomplete.

### 11.4 Project-Specific Detectors

- exact terms;
- case-insensitive terms;
- regular expressions;
- optional word boundaries;
- assignment of a data class and default action;
- YAML import and export.

Examples include customer names, internal project names, Java package prefixes, database table names, and domain terminology.

### 11.5 Payload Processing

- Recursively inspect all relevant text fields in JSON, including nested tool arguments and tool results.
- Preserve non-string values and JSON structure.
- Do not modify provider control fields such as model name or streaming flag without an explicit rule.
- Represent unsupported content as a dedicated finding type.
- Selectively inspect request headers for unexpected secrets. Handle known local authentication headers separately and never log them.

## 12. Redaction and Pseudonymization

### 12.1 Placeholders

Use typed, collision-resistant placeholders, for example:

```text
<AS:PERSON:0001>
<AS:ORGANIZATION:0001>
<AS:INTERNAL_CLASS:0001>
```

Equal values receive the same placeholder within a session. Different values must not share a placeholder.

### 12.2 Rehydration

- Only data classes explicitly configured as reversible may be rehydrated.
- Never rehydrate secrets, passwords, tokens, or private keys.
- Replace only exact placeholders generated by this proxy.
- Keep mappings locally, encrypted or in memory only, with a configurable TTL.
- When a mapping has expired, do not guess. Preserve unknown placeholders and emit a warning.
- Replacement must not corrupt JSON escaping or Unicode.

### 12.3 Default Behavior

- secrets: `BLOCK`;
- PII: `REDACT` by default in the balanced profile;
- project-specific terms: configurable;
- unsupported binary content: `BLOCK` in the strict profile.

## 13. Policy Engine

### 13.1 Profiles

#### `audit`

- Do not block content automatically unless an internal security failure makes safe forwarding impossible.
- Record findings and the hypothetical decision.
- Display a prominent notice that enforcement is disabled.

#### `balanced`

- Block secrets.
- Pseudonymize PII.
- Warn about or request approval for unknown sensitive terms.
- Warn about unsupported content.

#### `strict`

- Block secrets.
- Allow only approved providers and models.
- Require approval for or block unknown sensitive content.
- Block unsupported content.
- Block if a required detector is unavailable.

### 13.2 Rules

Rules may consider at least:

- agent or integration;
- project;
- provider;
- model;
- endpoint;
- direction: `REQUEST` or `RESPONSE`;
- finding category;
- severity;
- detector.

Version policies. Every decision references an immutable policy version. Support YAML import and export while SQLite remains the runtime source of truth.

## 14. Manual Approval

- For `REQUIRE_APPROVAL`, do not contact the provider yet.
- Create an approval request with a random ID and expiration time.
- Notify the dashboard using SSE or WebSocket.
- Show only the information required for the decision; keep secrets masked.
- The user can approve or deny once.
- One-time approval applies only to the concrete request fingerprint.
- Default timeout: 60 seconds, configurable.
- A timeout or coding-agent cancellation results in `BLOCK` or `CANCELLED`.
- Never send a request after its client has disconnected.
- Recurring approval requires an explicit new policy rule; never create one implicitly.

## 15. Persistence and Audit

### 15.1 Stored Audit Data

- UUID and timestamp;
- correlation ID and optional session ID;
- agent and project;
- provider, model, and endpoint;
- direction;
- request and response size;
- duration and proxy overhead;
- finding categories and counts;
- detectors and confidence;
- applied policy rules and policy version;
- decision and technical status;
- SHA-256 fingerprint of normalized content;
- error class without confidential error content.

### 15.2 Data Not Stored by Default

- complete prompts;
- complete LLM responses;
- provider credentials;
- local proxy tokens;
- detected secret values;
- reversible pseudonymization mappings beyond their TTL.

An explicit diagnostic mode may temporarily retain additional content. It must warn before activation, expire automatically, and still redact stored content.

### 15.3 Audit Export

- JSON export;
- standalone HTML report;
- no raw payloads by default;
- display the active filters and export period.

## 17. Agent Configuration and Diagnostics

### 17.1 Integration Principles

- Never overwrite existing configuration files blindly.
- Create a backup before modification.
- Preview the planned change.
- Apply changes atomically.
- Rollback restores the exact saved configuration.
- Do not remove unrelated user settings.

Because Codex and Claude Code configuration formats can change, implement integrations as independently tested adapters. Display supported versions and detected deviations.

### 17.2 `agentshield doctor`

Check at least:

- Python and platform prerequisites;
- port availability;
- write access to the local data directory;
- SQLite and migration status;
- native credential-store availability;
- presence of provider credentials without printing them;
- agent configuration and proxy endpoint;
- provider reachability through AgentShield;
- proxy loops;
- frontend build availability;
- active security profiles and detector status;
- warning about possible direct egress outside the proxy.

Output no secret values and return a meaningful exit code.

## 18. Quality and Security Requirements

### 18.1 Backend

- complete type annotations for application code;
- Pyright strict with no errors;
- Ruff check and format with no errors;
- no catch-all exception handling without safe logging and defined behavior;
- no confidential values in `repr`, exceptions, or logs;
- inject provider clients, clock, and persistence into tests.

### 18.2 Frontend

- TypeScript strict with no errors;
- accessible keyboard operation;
- no raw secrets rendered into the DOM;
- safe handling of long or binary-looking payloads;
- error boundaries and understandable failure states.

### 18.3 Tests

At minimum:

- unit tests for every detector;
- unit tests for policy precedence;
- round-trip tests for reversible pseudonymization;
- tests proving that secrets are never rehydrated;
- provider contract tests using local mock servers;
- SSE tests with fragmented events and fragmented findings;
- client cancellation during streaming and approval;
- provider errors, rate limits, and timeouts;
- concurrent requests and isolated session mappings;
- large payloads and size limits;
- Base64, URL encoding, Unicode, homoglyph, and zero-width cases;
- a false-positive corpus;
- tests proving logs and audit records contain none of the synthetic secrets;
- API security tests for Host, Origin, CORS, and local tokens;
- Playwright end-to-end tests for blocking, redaction, and approval;
- a macOS, Linux, and Windows CI matrix where supported by the selected CI system.

All provider tests must run without real provider credentials or paid API calls.

### 18.4 Performance Targets

On a current developer workstation without a heavy NLP detector:

- target median overhead before the upstream request: under 30 ms for small text requests;
- never buffer complete SSE responses;
- configurable hard request limit, initially 10 MiB;
- no unbounded queues or buffers.

Measure and document performance targets. They never justify silently bypassing a security check.

## 20. Definition of Done

Version 1 is complete only when all of the following are true:

1. A local mock coding agent can send OpenAI and Anthropic requests through the documented endpoints, and documentation makes no claim about controlling connections outside them.
2. Normal streaming and non-streaming requests reach the mock provider with correct semantics.
3. Synthetic secrets are blocked and demonstrably never reach the provider, logs, audit storage, or frontend.
4. Configured PII and internal terms can be pseudonymized, and eligible placeholders can be rehydrated correctly.
5. Secrets are never rehydrated.
6. `REQUIRE_APPROVAL` holds a request before the provider call and handles approval, denial, timeout, and client cancellation correctly.
7. The UI displays live events, findings, decisions, policies, integration status, and audit data.
8. Provider credentials are stored in the operating-system credential store and are not exposed to the coding agent or frontend.
9. Audit exports contain no raw payloads or secrets by default.
10. Configuration changes for supported agents provide preview, backup, validation, and rollback.
11. `agentshield doctor` identifies major configuration errors without exposing confidential data.
12. Backend and frontend linting, type checking, unit, integration, and end-to-end tests pass.
13. `docs/THREAT_MODEL.md`, `docs/ARCHITECTURE.md`, `SECURITY.md`, installation instructions, and the demo guide exist.
14. The UI and documentation visibly state that Version 1 does not enforce blocking of direct egress outside the proxy.

1. Start AgentShield.
2. Start the mock provider.

## 23. Implementation Rules

- Never make a feature work by silently disabling TLS verification, authentication, or failed scanners.
- Never place real credentials in source code, fixtures, screenshots, or documentation.
- Automated tests must not call external provider APIs.
- Do not introduce unnecessary microservices, message brokers, or cloud dependencies.
- Security and domain logic must be testable without the UI.
- New providers, detectors, and agent integrations must use explicit adapter interfaces.
- Record and justify any deviation from this specification in a short Architecture Decision Record.
- When requirements are ambiguous, choose the safer and simpler behavior and document the assumption.
